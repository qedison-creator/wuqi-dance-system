叁 / 03它是怎么工作的（大白话）Architecture
可换 · 皮肤层

三件"衣服"

每套皮肤 = 一张外观清单（颜色、圆角、阴影、字体、动效的取值表）+ 核心页面的一套布局样式 + 一组皮肤文案（如按钮写"立即预约"还是"立即锁定"）。全部是纯前端资源，打包进小程序。

共用 · 结构层

同一副"身体"

每个页面最外层挂一个"当前皮肤"类名（skin-classic / skin-paper / skin-volt），页面里的节点、点击事件、数据字段三套皮肤完全共用——同一个"预约"按钮，在三套皮肤里只是长得不一样，绑定的是同一个处理函数。

不碰 · 业务与数据层

账本不动

登录鉴权、网络请求、WebSocket、扫码签到、订阅消息、所有业务逻辑与后端接口一行不改。皮肤偏好只存本地一个新键 member_skin_id，不进数据库、不进后端。

  • 切换为什么能即时生效：会员点选 → 写入本地 + 更新全局皮肤变量 → 当前页重设类名 → 各页面在 onShow 时检测皮肤版本号自动刷新 → 自定义 TabBar 重绘 + 导航栏颜色跟随。全程 0.1 秒级，无白屏无重启。
  • 为什么不会弄丢数据：皮肤层根本接触不到数据。套餐、课时、约课、记录都在"业务与数据层"，那一层这次一行代码都不改；本地存储只新增一个键，已有的 token、用户信息等键零触碰。
  • 回退保险：读到未知皮肤值 → 自动按经典皮肤渲染并静默修正存储，永不白屏。

捌 / 08维护成本与交付方式Delivery
  • 日常改一处、三处生效：全局颜色/圆角/间距都收敛到"外观清单"，改按钮主色这类需求只改一张表；只有改核心 6 页布局时才需要分皮肤处理。
  • 新功能同步三套：后续新增页面默认按"令牌重涂"模式开发（自动获得三套配色），涉及新布局时三套皮肤同批交付，不留欠账。
  • 一次性交付：确认后整版实施——三套皮肤全部页面 + 切换功能 + 全量验证，随会员端下一次发版（并入当前未发布的版本批次）一起提审；后端无需随版发布。
  • 体积影响：新增的只有样式与少量 WXML/配置，无新依赖库，预计包体增量 <100KB，远低于分包上限。
